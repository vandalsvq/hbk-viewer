# Правила модулей форм 1С

Структура модуля, клиент-серверное разделение, директивы компиляции и работа с данными формы.

---

## Структура модуля

По стандарту 1С [«Структура модуля» (std455)](https://its.1c.ru/db/v8std/content/455/hdoc). Области **первого уровня** и их порядок — строго такие, пустых областей быть не должно:

```bsl
#Область ОписаниеПеременных
#КонецОбласти

#Область ОбработчикиСобытийФормы
// ПриСозданииНаСервере, ПриОткрытии, ПередЗакрытием
#КонецОбласти

#Область ОбработчикиСобытийЭлементовШапкиФормы
// всё, что не относится к таблицам формы
#КонецОбласти

#Область ОбработчикиСобытийЭлементовТаблицыФормы<ИмяТаблицыФормы>
// своя область на каждую таблицу формы: ...ТаблицыФормыДерево, ...ТаблицыФормыСписок
#КонецОбласти

#Область ОбработчикиКомандФормы
// процедуры из свойства Действие команд формы
#КонецОбласти

#Область СлужебныеПроцедурыИФункции
#КонецОбласти
```

Внутри области первого уровня объёмный код делится на подобласти **по смыслу** (`ЗагрузкаПакета`, `Индекс`, `Статья`) — это разрешено стандартом и приветствуется.

Чего делать нельзя:

- **группировать методы по «технологии»** — области `ВызовыСервера`, `КлиентскиеМетоды`, `БезКонтекста` запрещены стандартом прямо: такое упорядочивание затрудняет понимание логики. Серверная обёртка живёт рядом с клиентским методом, который её вызывает;
- вызывать один обработчик события из другого. Общее действие выносится в отдельную процедуру, которую вызывают оба обработчика;
- оставлять код вне областей.

Каждая переменная модуля снабжается комментарием в той же строке. В заголовке модуля формы рекомендуется описывать параметры формы.

Обработчики одного элемента располагаются вместе, в порядке их следования в панели свойств редактора формы.

## Строгая типизация

`// @strict-types` — первая строка нового модуля формы, как и любого другого модуля (полные правила: [`bsl-strict-types.md`](bsl-strict-types.md)). Типизация ловит частые баги форм: неявную смену типа реквизита, передачу не того типа в обработчик, `Перем` без инициализации.

В существующий модуль без директивы добавлять её при первом значимом расширении (примерно от 10 строк нового кода), а не ради формальности при косметической правке.

## Директивы компиляции

| Директива | Контекст | Когда использовать |
|---|---|---|
| `&НаКлиенте` | Клиент | Взаимодействие с UI, обработка ввода пользователя |
| `&НаСервере` | Сервер с контекстом формы | Когда нужно изменять реквизиты/элементы формы |
| `&НаСервереБезКонтекста` | Сервер без контекста | **Предпочтительно** для операций с данными — снижает объём передаваемых данных |
| `&НаКлиентеНаСервереБезКонтекста` | Клиент и сервер | Общие утилитарные функции |

**Правило:** Предпочитать `&НаСервереБезКонтекста` — не передаёт контекст формы на сервер.

### Суффикс «НаСервере» в именах

Каждый метод с директивой `&НаСервере` или `&НаСервереБезКонтекста` обязан иметь суффикс `НаСервере` в имени: по месту вызова сразу виден серверный round-trip, что упрощает ревью и помогает не вызывать сервер в цикле. Клиентские и клиент-серверные методы (`&НаКлиенте`, `&НаКлиентеНаСервереБезКонтекста`) — без суффикса.

```bsl
// Плохо: серверность не видна в месте вызова
&НаСервереБезКонтекста
Функция СписокПользователейИБ()

// Хорошо:
&НаСервереБезКонтекста
Функция СписокПользователейИБНаСервере()
```

## Клиент-серверное взаимодействие

- Не вызывать серверные методы в циклах на клиенте
- Собирать все нужные данные и передавать одним вызовом на сервер

```bsl
// Плохо: множественные серверные вызовы
&НаКлиенте
Процедура Обработать(Команда)
	Данные1 = ПолучитьДанные1НаСервере();
	Данные2 = ПолучитьДанные2НаСервере();
КонецПроцедуры

// Хорошо:
&НаКлиенте
Процедура Обработать(Команда)
	ВсеДанные = ПолучитьВсеДанныеНаСервере();
КонецПроцедуры

&НаСервереБезКонтекста
Функция ПолучитьВсеДанныеНаСервере()
	Результат = Новый Структура;
	Результат.Вставить("Данные1", ПолучитьДанные1());
	Результат.Вставить("Данные2", ПолучитьДанные2());
	Возврат Результат;
КонецФункции
```

## Данные формы

Использовать `ДанныеФормыВЗначение()` / `ЗначениеВДанныеФормы()` для конвертации между данными формы и объектами.

Реквизиты формы — это **не** то же самое, что реквизиты объекта: это представления, специфичные для формы.

### Обращение через ЭтотОбъект

К реквизитам **и методам** формы обращаться явно через `ЭтотОбъект.` — в большом модуле короткая форма неотличима от локальной переменной, а префикс сразу показывает, что значение живёт в форме и переживает обработчик (для методов — что вызов идёт у самой формы, а не глобальный).

```bsl
// Плохо: реквизит выглядит как локальная переменная
ИмяМакета = "Печать";

// Хорошо:
ЭтотОбъект.ИмяМакета = "Печать";
ЭтотОбъект.ОповеститьОВыборе(Результат);
ОбработкаОбъект = ЭтотОбъект.РеквизитФормыВЗначение("Объект");
```

Исключения: основной реквизит `Объект` и его подреквизиты (`Объект.НовыйКлючПараметров`) — без префикса; служебные коллекции формы (`Элементы`, `Команды`, `Параметры`) — тоже. В `&НаКлиентеНаСервереБезКонтекста`-хелперах форма приходит параметром — обращения `Форма.<Имя>`. Правило для нового кода; существующий массово не переписывать.

### Чтение параметров формы

Параметр, объявленный в схеме формы, читать по точке: `Параметры.ИмяПараметра`. Опциональный (в схеме отсутствует, передаётся ad-hoc через структуру открытия) — одной строкой через `ОбщегоНазначенияКлиентСервер.СвойствоСтруктуры(Параметры, "Имя", Дефолт)`. Старый паттерн `Параметры.Свойство("Имя", Перем)` с временной переменной не использовать: инициализация из четырёх параметров разрастается в 12+ строк с повторами имён.

```bsl
// Плохо: временная переменная и три строки на один параметр
ТекущийКлюч = "";
Параметры.Свойство("ТекущийКлюч", ТекущийКлюч);
Объект.ТекущийКлючПараметров = ТекущийКлюч;

// Хорошо: параметр из схемы формы — по точке
Объект.ТекущийКлючПараметров = Параметры.ТекущийКлюч;
// Хорошо: опциональный параметр — со значением по умолчанию
СсылкаНаМакет = ОбщегоНазначенияКлиентСервер.СвойствоСтруктуры(Параметры, "СсылкаНаМакет");
```

Компактную инициализацию из 3–5 параметров держать прямо в `ПриСозданииНаСервере` / `ИнициализацияФормы`; отдельная процедура оправдана только при логике сверх чтения параметров.

### Панель однотипных реквизитов: дефолты + мерж

Панель из ~5 и более однотипно заполняемых полей (превью настроек, шапка) не обслуживать парой методов «Очистить…»/«Заполнить…» с блоками `?(... = Неопределено, "", ...)` — список полей дублируется трижды. Вместо этого два метода `&НаКлиентеНаСервереБезКонтекста`: `ПустыеЗначения<Панель>()` возвращает структуру дефолтов правильных типов (единственное место со списком полей), а `Обновить<Панель>(Форма, знач Источник = Неопределено)` мержит источник поверх дефолтов и заливает в реквизиты одним циклом. Сброс панели — тот же вызов без источника.

```bsl
&НаКлиентеНаСервереБезКонтекста
Функция ПустыеЗначенияПанели()
	Значения = Новый Структура;
	Значения.Вставить("ОриентацияСтраницы", "");
	Значения.Вставить("МасштабПечати"     , 0);
	Значения.Вставить("ЧерноБелаяПечать"  , Ложь);
	Возврат Значения;
КонецФункции

&НаКлиентеНаСервереБезКонтекста
Процедура ОбновитьПанельНастроек(Форма, знач Источник = Неопределено)
	Значения = ПустыеЗначенияПанели();
	Если НЕ Источник = Неопределено Тогда
		Для Каждого Поле Из Значения Цикл
			Значения[Поле.Ключ] = ОбщегоНазначенияКлиентСервер.СвойствоСтруктуры(
				Источник, Поле.Ключ, Поле.Значение);
		КонецЦикла;
	КонецЕсли;
	Для Каждого Поле Из Значения Цикл
		Форма[Поле.Ключ] = Поле.Значение;
	КонецЦикла;
КонецПроцедуры
```

Имена ключей структуры дефолтов совпадают с именами реквизитов формы; если в источнике имена другие (XDTO-поля, поля БД) — предварительно построить структуру с правильными ключами. Нестандартную конвертацию отдельных полей (Булево → Число для радиокнопок) делать точечно до общего цикла мержа.

## Возврат результата формы

Форма, возвращающая результат по кнопке («Записать и закрыть», «Применить»), делает это парой `ОповеститьОВыборе` + `Закрыть` с проверкой `Открыта()`:

```bsl
&НаКлиенте
Процедура ЗаписатьИЗакрыть(Команда)

	Результат = Новый Структура;
	Результат.Вставить("НовыйКлюч", Объект.НовыйКлючПараметров);

	ЭтотОбъект.ОповеститьОВыборе(Результат);
	Если ЭтотОбъект.Открыта() Тогда
		ЭтотОбъект.Закрыть(Результат);
	КонецЕсли;

КонецПроцедуры
```

`ОповеститьОВыборе` — единый канал результата: работает и при модальном открытии (`РежимОткрытияОкнаФормы.БлокироватьОкноВладельца`), и при немодальном с обработчиком выбора. Проверка `Открыта()` обязательна: внешний обработчик `ОбработкаВыбора` мог уже закрыть форму в ответ на оповещение, и безусловный `Закрыть()` упадёт с исключением. Одинокий `Закрыть(Результат)` допустим лишь для формы, принципиально открываемой без обработчика выбора, но универсальный паттерн безопаснее по умолчанию.

## Асинхронные вызовы

Полные правила и паттерны: [`bsl-async.md`](bsl-async.md)

Новый клиентский код пишется на асинхронных методах платформы (8.3.18+), а не на колбэках с `ОписаниеОповещения`: линейный код вместо цепочки процедур-завершений, переменные диалога живут в одной области видимости, промежуточное состояние не пакуется в структуры `ДопПараметры`.

| Устарело (колбэк) | Современно (Асинх) |
|---|---|
| `ПоказатьВопрос(Оповещение, ...)` | `Ждать ВопросАсинх(...)` |
| `ПоказатьПредупреждение(Оповещение, ...)` | `Ждать ПредупреждениеАсинх(...)` |
| `ПоказатьВводЗначения(Оповещение, ...)` | `Ждать ВвестиЗначениеАсинх(...)` |
| `ПоказатьВводСтроки(Оповещение, ...)` | `Ждать ВвестиСтрокуАсинх(...)` |
| `Список.ПоказатьВыборЭлемента(Оповещение, ...)` | `Ждать Список.ВыбратьЭлементАсинх(...)` |
| `Список.ПоказатьОтметкуЭлементов(Оповещение, ...)` | `Ждать Список.ОтметитьЭлементыАсинх(...)` |

```bsl
&НаКлиенте
Асинх Процедура СкопироватьНастройки(Команда)
	Источник = Ждать СписокПользователей.ВыбратьЭлементАсинх(
		НСтр("ru = 'Пользователь-источник'; en = 'Source user'"));
	Если Источник = Неопределено Тогда
		Возврат;
	КонецЕсли;
	// ... линейное продолжение без процедур-завершений
КонецПроцедуры
```

Исключения и факты платформы:

- **Открытие формы Асинх-аналога не имеет**: функций `ОткрытьФормуАсинх` / `ОткрытьФормуМодальноАсинх` в платформе нет. Результат формы принимается через параметр `ОписаниеОповещения` в `ОткрытьФорму(...)`; модальное поведение — `РежимОткрытияОкнаФормы.БлокироватьОкноВладельца`.
- Выбор из списка — методы объекта `СписокЗначений` (`ВыбратьЭлементАсинх`, `ОтметитьЭлементыАсинх`); одноимённых глобальных функций нет.
- `Асинх`-процедуру вызывает либо платформа (обработчик команды), либо другой `Асинх`-код через `Ждать`; `Асинх`/`Ждать` работают только на клиенте.
- Существующие колбэк-обработчики не переписывать — правило для нового кода.

В докблоках тип формы — `ФормаКлиентскогоПриложения` (современное имя типа), не `УправляемаяФорма`.

Ключевые ограничения:
- Обработчики событий формы (`ПриОткрытии`, `ПередЗакрытием` и т.д.) нельзя объявлять как `Асинх` — параметр `Отказ` будет проигнорирован
- Для асинхронных операций при открытии/закрытии — вызывать отдельную `Асинх`-процедуру из обычного обработчика
- Обработчики команд (`&НаКлиенте`) — можно безопасно делать `Асинх`
