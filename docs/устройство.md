# Устройство обработки

Внешняя обработка, читающая пакет синтакс-помощника платформы (`shcntx_*.hbk`) **без внешних
утилит** - никаких `zip.exe`, `unzip.exe`, `V8Unpack.exe`. Всё делается штатными средствами
1С: контейнер разбирается вручную, хранилище статей открывается `ЧтениеZipФайла`, оглавление
распаковывается достройкой корректного zip вокруг внутренней записи.

Интерфейс штатный: дерево содержания с ленивой подгрузкой, индекс с поиском по русскому и
английскому имени, статья в поле HTML. Ссылки внутри статьи браузеру не отдаются - путь
вычисляется и статья открывается в том же поле. Иконки встроены в код как SVG.

## Клиент и сервер

Работа с данными пакета - клиент-серверная: `engine_data.bsl` компилируется и туда, и туда
(`&НаКлиентеНаСервереБезКонтекста`), а **где именно читать - решается по доступности файла**.

| Где | Что происходит |
| --- | --- |
| Тонкий и толстый клиенты | читают сами: пакет лежит рядом с клиентом, это его установка платформы |
| Клиент файл не видит | уходим на сервер: другая машина, другая ОС, сетевой каталог - `shcntx_*.hbk` ставится в тот же `bin`, что и `rphost.exe` |
| Веб-клиент | файлов не видит вовсе, поэтому только сервер |
| Отладка со строгой проверкой | клиенту файлы запрещены - это не ошибка, просто уходим на сервер |

В веб-клиенте каждый метод работы с данными отказывает **явным исключением с именем метода**
(`ВебКлиентНеПоддерживается`), а не молчаливой заглушкой: иначе причина теряется. Вызывающий
это исключение ловит и переходит на серверный путь. Если пакета нет и там - сообщает
пользователю. Передачу файла на сервер из веб-клиента прототип не делает: это задача
вызывающей стороны.

Вызовы сервера без состояния, потому что при открытии клиент забирает всё, что ему нужно:

| Что | Размер | Кто делает |
| --- | --- | --- |
| Текст оглавления | 4,5 МБ | распаковывается, разбирается на клиенте |
| Индекс статей (путь, смещение, размер) | 2,4 МБ | читается из каталога архива, разбирается на клиенте |
| Статья | 1-3 КБ | читается одна запись по готовому смещению |

Когда работает клиент, передачи нет вовсе - вызовы локальные.

## Состав

| Файл | Назначение |
| --- | --- |
| `engine_data.bsl` | работа с данными: поиск пакета, подготовка, чтение статьи по смещению |
| `engine_client.bsl` | разбор оглавления и индекса, дерево, поиск, виды узлов |
| `form_ui.bsl` | обработчики формы: ленивое дерево, поиск, история переходов, ссылки статьи |
| `icons/*.svg` | иконки видов узлов - раздел, объект, метод, свойство, событие, статья |
| `icons_to_bsl.py` | собирает `icons.bsl` из svg (base64 внутри кода, макеты не нужны) |
| `icons.bsl` | сгенерированный модуль иконок - править нужно svg |
| `form_layout.xml` | разметка формы в формате платформы - правится в конфигураторе |
| `formsrc.py` | единый источник разметки и склейки модуля для обеих сборок |
| `build_epf.py` | собирает `.epf` конфигуратором в батче |
| `import_form.py` | забирает изменённую в конфигураторе разметку обратно в исходники |
| `build_check.py` | headless-проверка формы: та же форма общей формой в тестовой конфигурации |
| `form_check.bsl` | самопроверка формы (36 проверок), только для `build_check.py` |
| `check_app.bsl` | драйвер прогона в модуле управляемого приложения тестовой конфигурации |
| `check_server.bsl` | серверная часть стенда: пишет отчёт и трассу, клиенту файлы запрещены |
| `test_engine.bsl` | стенд движка с замерами, гоняется через `tools/run.py` |
| `test_books.bsl` | стенд: что лежит в других пакетах справки платформы |

Форму правим в конфигураторе, код - в `.bsl`. Дорога в обе стороны:
`build_epf.py` собирает обработку из `form_layout.xml`, `import_form.py` возвращает
изменённую разметку в исходники. Модуль формы в конфигураторе править бесполезно -
он собирается из файлов; `import_form.py` предупредит, если код разошёлся.

```powershell
python tools\icons_to_bsl.py
python tools\build_epf.py
python tools\dump_epf.py           # выгрузка обработки в файлы для конфигуратора
python tools\import_form.py        # после правки формы в конфигураторе

# проверка формы целиком, ~25 секунд на цикл, кликов не требует
python tools\build_check.py
python tools\build_check.py --окно      # то же, но окно предприятия остаётся на экране
python tools\build_check.py --толстый   # без строгого режима, если надо сравнить

# стенд движка с замерами, ~10 секунд на цикл
python tools\run.py tools\test_engine.bsl src\engine_data.bsl src\engine_client.bsl
```

## Как устроена headless-проверка

`build_check.py` кладёт **ту же самую форму** общей формой в одноразовую тестовую
конфигурацию, грузит её конфигуратором, гоняет `/CheckModules` и запускает тонкий клиент
с ключами `/EnableCheckModal /EnableCheckSyncCalls /EnableCheckExtensionsAndAddInsSyncCalls` -
теми же, что включает конфигуратор при отладке. Модуль управляемого приложения
(`check_app.bsl`) открывает форму, дожидается загрузки пакета, вызывает `Самопроверка()`
из `form_check.bsl` и завершает работу. Отчёт - в `%TEMP%\hbk_check.log`, ход прогона -
в `%TEMP%\hbk_check_trace.log`.

XML формы для обработки и для проверки берётся из одного `formsrc.py`, отличается
только реквизитом `Объект`: у общей формы основного реквизита нет.

Чтение статьи по смещению вместо штатного поиска в `ЧтениеZipФайла` - это 7 мс против
110 мс и никакой карты путей на 620 мс: на 52 тысячах элементов штатный поиск идёт перебором.

**Почему клиент пробуется первым.** Сервер не быстрее: это тот же код плюс накладные
расходы вызова (около 8 мс на статью) и семь мегабайт по проводу при открытии
(оглавление 4,5 МБ и индекс 2,4 МБ). Промах клиента стоит почти ничего - файл не нашёлся,
уходим на сервер.

Узлы оглавления раскладываются по видам: свойств 12 241, методов 8 363, статей 3 649,
объектов 2 355, разделов 922, событий 830.

Подробности формата `.hbk` и заметки по скорости `ЧтениеZipФайла` -
в [«Формат пакета справки»](формат-hbk.md).

## Грабли, на которые уже наступили

Всё это ловится прогоном `build_check.py`, но не ловится ни загрузкой XML, ни `/CheckModules`.

- **Вид поля задаётся именем XML-элемента**, а не вложенным `<Type>`: колонки таблицы -
  это `<InputField>` и `<PictureField>`, надпись - `<LabelField>`. Элемента `<Field>` не
  существует: платформа молча выбрасывает его при загрузке, и таблица открывается без колонок.
- **Локальные переменные не должны называться как свойства формы** (`Заголовок`, `Элементы`,
  `Команды`, `Параметры`, `Окно`): присваивание уходит в свойство формы. Именно поэтому
  движок падал в форме, работая в модуле приложения.
- **`ПодключитьОбработчикОжидания` с интервалом меньше секунды** требует третьего параметра
  `Истина`, а процедура модуля приложения должна быть экспортной.
- **Второй параметр `ЗавершитьРаботуСистемы` - это перезапуск**, а не принудительность:
  прогон с ним зацикливается и выедает лицензии разработчика.
- **Код возврата `/CheckModules` не отражает ошибки** - смотреть надо протокол.
- **`Новый Файл(...)` нельзя разыменовывать на месте** - нужна промежуточная переменная.
- **`Формат(0, "ЧГ=0")` возвращает пустую строку**: у нуля по умолчанию пустое
  представление, нужен `ЧН=0`. Первая запись архива лежит ровно по нулевому смещению.
- **Однобайтовая кодировка для разбора двоичных данных - только `ISO-8859-1`**: она
  отображает все 256 байт один в один, `windows-1251` этого не гарантирует.
- **Тонкий клиент без ключей строгого режима пропускает запрещённые вызовы** - гонять
  проверку надо именно с ними, иначе ошибка вылезет уже у пользователя.
- **В `ПередРазворачиванием` приходит идентификатор строки**, а не сама строка. Проверять
  такие вещи надо настоящим действием (`Элементы.Дерево.Развернуть`), а не вызовом
  обработчика: подменив параметр удобным значением, проверяешь не то, что происходит.
- **Экспортные методы модуля управляемого приложения попадают в глобальный контекст**
  и сталкиваются с одноимёнными методами форм той же конфигурации.
