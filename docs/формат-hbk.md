# Формат пакета справки .hbk

Всё, что удалось выяснить о контейнере справки платформы. Проверено на 8.3.27.2214,
пакет `shcntx_ru.hbk` (синтакс-помощник, 38,9 МБ). Формат недокументирован, поэтому
здесь только то, что подтверждено чтением живых файлов.

## Контейнер

`.hbk` - контейнер того же формата, что `.epf` и `.cf`: 16 байт заголовка, дальше блоки
с 31-байтовой ascii-шапкой (`\r\n` + три шестнадцатеричных числа по 8 знаков + `\r\n`):
размер документа, размер блока, адрес следующего блока. Таблица сущностей лежит по
смещению 47, по 12 байт на запись: адрес заголовка, адрес тела и признак `2147483647`.
Имя сущности - в теле заголовка, начиная с 21-го байта, в UTF-16LE.

Адрес `2147483647` означает «сущности нет» - у мелких пакетов так помечены индексные
сущности, и читатель обязан это проверять, иначе прочитает мусор.

## Сущности

Их семь, и одинаковый набор у всех пакетов платформы:

| Сущность | Размер в `shcntx_ru` | Содержимое |
| --- | --- | --- |
| `FileStorage` | 38,4 МБ | валидный ZIP: 52 064 записи, из них 25 511 HTML-статей |
| `PackBlock` | 677 КБ | оглавление: одна deflate-запись, разворачивается в 5,2 МБ текста |
| `IndexPackBlock` | 1,2 МБ | предметный указатель: 91 deflate-запись, 9,15 МБ текста |
| `PackLookup` | 222 КБ | номер узла → номер записи в паке, плюс разрежённая таблица через 128 |
| `MainData` | 56 байт | число узлов, число корней и номера корневых узлов |
| `IndexMainData` | 44 байта | головы алфавитных цепочек указателя по языкам |
| `Book` | 298 байт | имя книги, заголовок и список продуктов `CONF_ENTERPRISE`, … |

Полнотекстового индекса в пакете **нет** - ни в одном из 40 пакетов справки платформы.
Указатель конфигуратора лежит вне пакета, в профиле пользователя
(`%LOCALAPPDATA%\1C\1cv8\helpsynt.dat`, UTF-16BE со сжатием по общему префиксу), и там
тоже только имена: слов из текстов статей в нём нет.

## Оглавление (`PackBlock`)

Одна локальная запись zip без центрального каталога, поэтому штатным `ЧтениеZipФайла`
её не открыть - вокруг записи достраивается корректный архив (локальная запись + запись
центрального каталога + EOCD), и дальше работает платформа.

Текст начинается с числа узлов, дальше идут узлы. Узел даёт всё нужное - номер,
родителя, число детей, их номера, локализованные имена и путь статьи:

```text
{27449,27407,3,27450,27453,27473,
{1,1,
{1,2,
{"ru","ТаблицаЗначений"},
{"en","ValueTable"}
},"/objects/catalog234/catalog236/ValueTable.html"}
},
```

Служебные разделы вместо пары `ru`/`en` несут `{"#","Свойства"}` и пустой путь.
В мелких пакетах (язык запросов, компоновка данных) язык `#` стоит у **всех** узлов.

Путей в оглавлении 25 514, и все они находятся в архиве статей.

## Предметный указатель (`IndexPackBlock`)

То, что конфигуратор показывает на вкладке «Индекс». 91 запись zip, 28 578 элементов,
почти все двуязычные - итого 57 123 имени и 42 955 ссылок на 24 784 статьи.

```text
{6,1,2,"en",6160,0,"en",6149,0,"en","WebSocketClients",0,
      "ru",4,0,"ru",12455,0,"ru","WebSocketКлиенты",0,1,0,2,"/objects/…13939.html","/objects/…13967.html"}
```

Номер, число языков, дальше на каждый язык - соседи по алфавиту и имя, затем число
целей и пути статей. Соседи образуют готовый двусвязный список в алфавитном порядке,
сортировать ничего не нужно. Короткое имя и полное имя с владельцем - **разные
элементы**, поэтому в конфигураторе находится и `Структура`, и `ТаблицаЗначений.Добавить`.

## Доступность статьи

Признак доступности («Тонкий клиент, веб-клиент, мобильный клиент, толстый клиент…»)
лежит **только в тексте статьи**. Ни в оглавлении, ни в указателе его нет: поле, похожее
на маску, у всех 28 578 элементов указателя одинаковое. Список продуктов в `Book` -
словарь возможных значений, а не признак у конкретной статьи. Поэтому отбор по
доступности стоит полного прохода по статьям - ровно как и собственный полнотекстовый
поиск, и делать их разумно вместе.

## Замеры (8.3.27.2214, Windows, файловая ИБ)

| Шаг | Время |
| --- | --- |
| Поиск пакета справки по каталогам платформы | 0 мс |
| Разбор таблицы сущностей контейнера | 0 мс |
| Вырезание `FileStorage` (38,4 МБ) потоковым копированием | 0 мс, если файл уже вырезан |
| Чтение оглавления (распаковка + текст 4,56 млн символов) | 47 мс |
| Индекс архива по центральному каталогу (52 064 записи) | 321 мс |
| Разбор оглавления в 28 360 узлов | 871 мс |
| Разбор индекса статей | 165 мс |
| **Открытие пакета целиком** | **около 1,4 секунды** |
| Дети узла при разворачивании дерева | 0-1 мс |
| Поиск по префиксу имени (русскому или английскому) | 72 мс |
| Статья: чтение и распаковка одной записи | 7 мс на клиенте, 15 мс через сервер |
| Повторный показ статьи (из кеша) | 0 мс |

Память: файл читается потоком, в памяти живут только индексы оглавления. Статьи лежат
на диске и извлекаются по одной. Вырезанный `FileStorage` переиспользуется между
сеансами: если файл нужного размера уже готов, шаг вырезания пропускается.

## Почему не используется поиск в `ЧтениеZipФайла`

Замеры на архиве из 52 064 элементов: стоимость извлечения зависит от того, **как
получен элемент**.

| Способ | Время на статью |
| --- | --- |
| Извлечение прямо внутри `Для Каждого … Из Архив.Элементы` | 6 мс |
| По ранее сохранённой ссылке на элемент | 110 мс |
| По индексу `Архив.Элементы[Индекс]` | 348 мс |
| `Архив.Элементы.Найти(Имя)` перед извлечением | +480 мс |

Похоже, платформа ищет элемент перебором коллекции, если он не является текущим в
обходе. Поэтому `Найти` не используется вовсе: центральный каталог архива разбирается
самостоятельно, из него берутся смещение и размер записи, и дальше читается ровно одна
запись - 7 мс вместо 110.

Полная распаковка архива дала бы 0,15 мс на статью, но стоит **70 секунд** и 71,4 МБ
на диске (52 064 файла) - для разового открытия справки это неприемлемо.

## Статьи

Самодостаточны: в выборке из 400 статей ни одного `<img>` и ни одной ссылки на css,
у всех есть заголовок. Значит статья показывается присваиванием HTML-строки в поле, без
локальных ресурсов - предупреждение платформы об открытии локального файла не возникает.

Ссылки внутри статьи бывают двух видов: абсолютные
`v8help://SyntaxHelperContext/objects/catalog234/ValueTableRow.html` (первый сегмент -
имя книги) и относительные `ValueTable/methods/Add110.html` от каталога текущей статьи.
