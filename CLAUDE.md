# CLAUDE.md

Руководство для работы Claude Code над этим проектом.

## Проект

**Просмотр справки 1С** — внешняя обработка, открывающая пакеты справки платформы
(`.hbk`) прямо из 1С:Предприятия. Читает контейнер средствами самой 1С, без внешних
утилит и компонент.

- Это **не** EDT-проект и не расширение конфигурации: одна внешняя обработка с одной формой
- Платформа: 1C:Enterprise 8.3.14+, проверяется на 8.3.27
- Задачи: <https://github.com/vandalsvq/hbk-viewer/issues>

Почему не EDT: сборка нужна одной командой пакетного конфигуратора, без Ring, Java и
самой EDT. Обработку из одной формы EDT ничем не улучшает, а порог входа поднимает.
Исходники модулей — обычные `.bsl`, при необходимости открываются в EDT импортом `.epf`.

## Раскладка

```text
src/                исходники обработки — единственное место, где правится код
  form_ui.bsl         обработчики формы
  engine_client.bsl   разбор оглавления и указателя, поиск, виды узлов
  engine_data.bsl     работа с файлами
  icons.bsl           сгенерирован из src/icons/*.svg — править нужно svg
  form_layout.xml     разметка формы в формате платформы
  object_module.bsl   модуль объекта: версия обработки
tools/              сборка и автономные стенды
dist/               результат сборки: .epf и выгрузка в файлы
docs/               формат .hbk, устройство, стандарты кода BSL
```

`dist/` — результат сборки, руками не правится. `icons.bsl` — тоже.

## Архитектура: что от чего зависит

| Файл | Что делает | Чего не делает |
| --- | --- | --- |
| `engine_data.bsl` | всё, что трогает файлы: поиск пакета, распаковка, чтение статьи | не знает про форму, не разбирает тексты |
| `engine_client.bsl` | разбор оглавления и указателя, дерево, поиск | **не трогает файлы вовсе** |
| `form_ui.bsl` | интерфейс: дерево, индекс, статья, навигация | не разбирает форматы, не читает файлы |

Разделение не косметическое: `engine_data.bsl` компилируется и на клиенте, и на сервере
(`&НаКлиентеНаСервереБезКонтекста`), а `engine_client.bsl` — только на клиенте. Появление
файловой операции в разборе или разбора в файловой части ломает эту схему.

Вызовы сервера **без состояния**: всё, что нужно для чтения статьи, приносит вызывающий.

В веб-клиенте файловые методы обязаны отказывать через `ВебКлиентНеПоддерживается(ИмяМетода)` —
явным исключением с именем метода, а не молчаливой заглушкой. Служебная часть
`engine_data.bsl` целиком выключена директивой препроцессора: иначе модуль не соберётся
под веб-клиент, где нет ни `ФайловыеПотоки`, ни `ЧтениеZipФайла`.

## Сборка и проверка

```powershell
python tools\build_epf.py          # собрать dist\hbk-viewer.epf
python tools\dump_epf.py           # выгрузка обработки в файлы (для конфигуратора)
python tools\build_check.py        # проверка формы целиком, ~25 с, кликов не требует
python tools\build_check.py --окно # то же, но окно предприятия остаётся на экране
python tools\import_form.py        # забрать разметку формы после правки в конфигураторе
python tools\icons_to_bsl.py       # пересобрать icons.bsl из svg

# стенд движка с замерами, ~10 с на цикл
python tools\run.py tools\test_engine.bsl src\engine_data.bsl src\engine_client.bsl
```

Платформа ищется сама (самая свежая установленная), переопределяется переменной `HBK_1C`.
Рабочий каталог стендов — `HBK_WORK`, по умолчанию временный каталог системы. Ничего
машинно-зависимого в скриптах быть не должно — всё в `tools/стенд.py`.

**После любой правки кода — `tools\build_check.py`.** Это не формальность: проверка ловит
то, что не ловят ни загрузка XML, ни `/CheckModules`, — потерянные элементы формы,
запрещённые в строгом режиме вызовы, поведение событий. Прогон гоняет тонкий клиент
с ключами строгого режима и проверяет компиляцию под веб-клиент.

Форма правится в конфигураторе и возвращается в исходники через `import_form.py`.
Модуль формы в конфигураторе править бесполезно — он собирается из `.bsl`.

## Соглашения по коду

- Язык кода и комментариев — **русский**; имена переменных, процедур, реквизитов — тоже
- В комментариях только дефис `-`, длинное тире не использовать
- `знач` — строчными
- `#Область` и `#КонецОбласти` отделяются от соседних комментариев пустой строкой
- Пользовательские тексты — через `НСтр("ru = '…'")`, не голым литералом

**Структура модуля формы** — по стандарту 1С (std455), области первого уровня и порядок:
`ОписаниеПеременных`, `ОбработчикиСобытийФормы`, `ОбработчикиСобытийЭлементовШапкиФормы`,
`ОбработчикиСобытийЭлементовТаблицыФормы<Имя>` (своя на каждую таблицу),
`ОбработчикиКомандФормы`, `СлужебныеПроцедурыИФункции`. Внутри — подобласти по смыслу.
Группировать методы по серверности стандарт запрещает: серверная обёртка живёт рядом
с методом, который её вызывает. Подробности — [`docs/bsl-form-module-rules.md`](docs/bsl-form-module-rules.md).

Метод с директивой `&НаСервере` / `&НаСервереБезКонтекста` обязан оканчиваться на
`НаСервере` — чтобы серверный вызов был виден в месте вызова.

Метод принимает **один тип** на параметр: разбирать «идентификатор или строка» должен
вызывающий, а не метод.

Полные руководства по BSL — в [`docs/`](docs/): стандарты, антипаттерны, модули форм,
строгая типизация, асинхронные методы.

## Ветки, коммиты, версия

- Основная ветка: `main`
- Рабочие ветки: `feature/<N>` от `main`, где `N` — номер issue
- Формат коммита: `https://github.com/vandalsvq/hbk-viewer/issues/<N> <описание на русском>`
- Не добавлять `Co-Authored-By`
- `git push` — только по явной просьбе владельца

**Версия обработки** — `Функция Версия()` в `src/object_module.bsl`, совпадает с тегом
релиза. Поднимается в коммите, который закрывает задачу.

Собранная обработка в `dist/` обновляется перед релизом, а не в каждом коммите.

Имя объекта метаданных русское (`ПросмотрСправкиHBK`), а имя файла — латиницей
(`hbk-viewer.epf`): GitHub вырезает кириллицу из имён файлов, приложенных к релизу.
На файлы внутри репозитория это не распространяется.

## Порядок работы

1. Значимое изменение начинается со спецификации в [`specs/`](specs/) — процесс
   и шаблоны там же. Опечатка, локальный багфикс, рефакторинг без изменения поведения
   спеки не требуют
2. Перед правкой — `Grep` для поиска, затем `Read`
3. Не смешивать слои: файлы — в `engine_data.bsl`, разбор — в `engine_client.bsl`,
   интерфейс — в `form_ui.bsl`
4. После правки — `tools\build_check.py`, все проверки должны быть зелёными
5. Расхождение кода и спеки — правится спека тем же изменением
6. Коммит атомарный, со ссылкой на issue
