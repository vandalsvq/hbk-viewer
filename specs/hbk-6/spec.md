# hbk-6: Разработка в EDT

> Ссылка на issue: `https://github.com/vandalsvq/hbk-viewer/issues/6`

## 1. Контекст и проблема

Руководства в [`docs/`](../../docs/) - строгая типизация, стандарты, правила модуля
формы - написаны под валидатор EDT. Проверять их сейчас некому: правила есть,
автоматического контроля нет, соблюдение держится на дисциплине ассистента. Ревью
владельца показывает, что этого не хватает - правки идут в основном по типизации.

Второе: слои живут тремя `.bsl`, которые `tools/formsrc.py` склеивает в один модуль
формы. Для любого инструмента это один большой текст - ни навигации, ни вывода типов.

Причина такой схемы - платформенная: **у внешней обработки нет общих модулей**, ни в
конфигураторе, ни в EDT. Разделение `engine_data` / `engine_client` / `form_ui`
держится на сборщике, а не на платформе.

Отсюда развилка: чтобы получить настоящие модули и типизацию, исходники должны быть
конфигурацией, а внешняя обработка - результатом сборки, а не источником.

## 2. Область изменений

| Компонент | Тип | Характер изменений |
| --- | --- | --- |
| `src/*.bsl` | исходники | переезжают в EDT-проект общими модулями |
| EDT-проект | новое | конфигурация: общие модули, общая форма |
| `tools/build_epf.py` | сборка | берёт модули из EDT-раскладки, склейка сохраняется |
| `tools/formsrc.py` | сборка | пути к исходникам, директивы и `Экспорт` при склейке |
| `tools/build_check.py` | проверка | берёт модули оттуда же |
| `tools/lint.py` | новое | проверка правил `docs/` без Java |
| `CLAUDE.md`, `README.md` | документация | новый порядок работы, отмена мотивировки «не EDT», минимум платформы 8.3.18 |

**Проверка архитектурных ограничений:**

- [x] Разделение слоёв сохраняется и усиливается: то, что было соглашением
      сборщика, становится границей модулей
- [x] Поставка не меняется: остаётся `.epf`, открываемая в любой базе
- [x] Java, Ring и `edtcli` в обязательной сборке не появляются

## 3. Поведение

Задача инфраструктурная: поведение обработки для пользователя не меняется ни в чём.
«Поведением» здесь является порядок разработки.

### 3.1. Основной сценарий разработки

1. Разработчик правит общий модуль в EDT. Работают навигация, вывод типов,
   валидация `// @strict-types`.
2. `python tools\lint.py` проверяет правила `docs/`, которые EDT не проверяет:
   структура областей, суффикс `НаСервере`, `НСтр`, оформление комментариев.
3. `python tools\build_check.py` собирает тестовую конфигурацию и гоняет форму -
   как сейчас, но модули берёт из EDT-раскладки.
4. `python tools\build_epf.py` собирает `.epf` склейкой модулей в модуль формы.
   Нужен только под релиз.

### 3.2. Что даёт склейка и почему она остаётся

Общий модуль и модуль формы отличаются двумя вещами, и обе уже умеет `formsrc.py`:

- **директивы компиляции**: в общем модуле их нет (серверность задаётся свойствами
  модуля), в модуле формы они обязательны у каждого метода - сборщик их проставляет;
- **`Экспорт`**: в общем модуле нужен у публичных методов, в модуле формы у серверных
  не компилируется - сборщик его снимает.

Поэтому один и тот же текст `.bsl` работает и общим модулем, и частью модуля формы.
Это же означает, что переезд не требует переписывания кода - только раскладки.

### 3.3. Граничный случай: форма

Единственное место, где форматы расходятся. Модули EDT хранит обычными `.bsl`, а
форму - в собственном формате; сборке `.epf` нужна разметка в формате платформы
(`src/form_layout.xml`, правится в конфигураторе, возвращается `import_form.py`).

Конвертация между форматами - это ровно то, ради чего понадобился бы `edtcli`.
Поэтому форма выносится за первый этап: движок переезжает в общие модули, форма
остаётся в текущей схеме. Решение по форме принимается отдельно, когда станет
понятно, сколько стоит ручная синхронизация разметки (меняется она редко).

### 3.4. Ошибки

- Расхождение модуля в EDT и в сборке невозможно: источник один, копий нет.
- Если EDT не установлена, разработка продолжается: сборка, `build_check` и
  `lint.py` от EDT не зависят. Теряется только валидация типов.

## 4. Контракты

### 4.1. Раскладка репозитория

Точные имена каталогов EDT уточняются при первом импорте проекта - в спеку
переносятся после проверки, а не по памяти.

```text
<edt-проект>/src/CommonModules/<Модуль>/Module.bsl   исходники движка
src/form_layout.xml                                  разметка формы (формат платформы)
src/form_ui.bsl                                      модуль формы до решения по 3.3
tools/                                               сборка, проверки, линтер
dist/                                                результат сборки
```

### 4.2. Модули

| Модуль | Клиент | Сервер | Содержимое |
| --- | --- | --- | --- |
| `ДвижокСправкиДанные` | да | да | файловые операции, `engine_data.bsl` |
| `ДвижокСправкиРазбор` | да | нет | разбор оглавления и указателя, `engine_client.bsl` |
| `ИконкиСправки` | да | нет | сгенерированные картинки, `icons.bsl` |

Имена - предмет согласования на этапе спеки, не результат реализации.

### 4.3. `tools/lint.py`

Проверяет то, что EDT не знает, - правила проекта. Набор собран из части II
[`code-review.md`](code-review.md): перенимается всё, включая двуязычный `НСтр`.

- doc-блок с секциями `Параметры` и `Возвращаемое значение` у каждого метода,
  включая неэкспортные; структуры описываются ссылкой `см. <Конструктор>`, а не прозой;
- функция-конструктор у каждой структуры, пересекающей границу метода;
- виды узлов и префиксы пакетов - не строковыми литералами по коду;
- `НСтр` в двуязычном формате `НСтр("ru='…';en='…'")` вместо голых литералов;
- суффикс `НаСервере` у методов с серверной директивой;
- порядок и состав областей модуля формы (std455);
- `ЗначениеЗаполнено()` вместо `Количество() > 0` и `Количество() = 0`;
- `НЕ` и `ИЛИ` заглавными; шапка модуля обычными `//`, а не баннером из `////`;
  выравнивание doc-блоков табами;
- `знач` строчными, дефис вместо длинного тире;
- пустая строка вокруг `#Область` / `#КонецОбласти`.

Двуязычный `НСтр` означает перевод интерфейса на английский - все 22 текущих вызова
и все будущие. Это принятое решение, а не побочный эффект: правило распространяется
и на тексты, которых сейчас нет.

Выход - список нарушений с `файл:строка`, код возврата ненулевой при находках.

## 5. Критерии приёмки

- [ ] EDT-проект открывается, движок лежит общими модулями, валидация проходит
- [ ] `// @strict-types` включён в перенесённых модулях, doc-блоки полные
- [ ] `python tools\build_epf.py` собирает `.epf` из тех же модулей
- [ ] Собранная `.epf` открывается в базе и работает как до переезда
- [ ] `python tools\build_check.py` зелёный, включая компиляцию под веб-клиент
- [ ] `python tools\lint.py` запускается отдельно и внутри `build_check`, находки не игнорируются
- [ ] Java, Ring и `edtcli` не нужны ни для одной команды сборки и проверки
- [ ] Нижняя граница платформы поднята до 8.3.18; `CLAUDE.md` и `README.md` это отражают
- [ ] Диалог выбора файла переведён на `Асинх` / `Ждать` вместо `ОписаниеОповещения`
- [ ] Пользовательские тексты - в двуязычном `НСтр`
- [ ] `CLAUDE.md` описывает новый порядок; прежняя мотивировка «почему не EDT» заменена
- [ ] На каждом шаге переезда дерево остаётся собираемым

## 6. Вне области

- Смена формата поставки: остаётся внешняя обработка `.epf`
- Ring и `edtcli` в обязательной сборке
- Перевод формы в формат EDT - отдельное решение после этапа 1 (см. 3.3)
- Функциональные изменения: поведение обработки не меняется
- Автоматические тесты (YAxUnit, Vanessa) - отдельная задача
